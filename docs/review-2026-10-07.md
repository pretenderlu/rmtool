## 已确认的问题

以下 7 项均有本地隔离复现。P1 应优先修复；P2 是明确的可靠性问题。
行号对应本次审阅的代码基线。

### R1 / P1：已完成的固件事务会再次锁住后续正常升级

位置：`_firmware.py:580`、`_firmware.py:586`，以及连接检查 `_firmware.py:633`。

`query_transaction()` 确认重启进入目标系统后，只返回 `completed`，
没有持久化终态或解除 `current` 对旧任务的引用。下一次连接仍将当前系统与
该任务的历史目标分区、版本和 xochitl 哈希比较。用户随后通过官方方式升级，
或在 rmtool 之外正常切换系统，旧任务就可能重新变成 `unknown`，
导致插件、字体和普通设备操作被统一阻止。

复现：同一个假设备先正常完成 `.172` 事务，再模拟无待更新、无错误计数的
后续官方更新，结果为 `completed -> unknown`，`firmware_guard_reason` 重新出现。
`3.29.0.100` 仅为检查脚本中的合成版本，不是对官方版本的声明。

最小修复：首次取得完整的启动后证据时，原子写入已完成记录或归档当前事务。
以后保留历史日志，但不要把已完成任务重新作为活动任务；仍需独立检查当前
系统是否有进行中的更新。不能无条件删除结果不明或失败的任务。

### R3 / P1：异常文档标识能把单篇删除扩大为整库删除

位置：`rmtool.py:458`、`_tab_documents.py:1034`。

文档列表直接把 `.metadata` 文件名前缀作为标识，删除时将标识拼入未引用的
`rm -rf` 和通配符表达式。设备端如果有 `*.metadata` 这样的异常文件，
它会成为可选择的文档，而单篇删除会生成整个文档根目录的通配删除命令。
空标识和 shell 特殊字符也没有在此边界拒绝。

复现仅记录生成的命令，**没有实际执行删除**。普通 UUID 文件名不会触发此问题；
风险来自第三方工具、异常恢复或不可信目录内容。

最小修复：在文档读取和删除边界验证 UUID；按已确认的文件/目录清单删除，
对路径使用 shell 引用，不让文档标识参与 shell 表达式。

### R4 / P1：KOReader 的排队删除可能落到另一台设备

位置：`_tab_koreader.py:1158`、`_tab_koreader.py:1177`。

确认删除后，Worker 只保存路径和书库根目录，没有保存 SSH 连接身份。
进度窗为非模态；用户断开 A 并连接 B 后，排队任务或多步任务的后续步骤
会使用共享 wrapper 的新连接。如果 B 的同路径存在书籍，会删除 B 的书籍。
路径边界检查无法分辨两个设备上的相同路径。

复现：在两个内存假设备上放置相同路径，A 创建的排队操作执行前切到 B，
A 的文件保留，B 的文件被删除。无需真实设备。

最小修复：沿用 `_tab_documents.py:1025` 和共享插件恢复页已有的模式，
捕获连接 token，在取得 `operation_session()` 后校验，并持锁执行整批操作。
同类上传、新建目录和延迟返回的列表也应一起检查，不另建任务框架。

### R2 / P2：固件锁生效时，“刷新设备状态”自身也被锁住

位置：`_tab_firmware.py:409`。

`refresh()` 在进入有受控豁免的 `firmware.inspect_device()` 之前，
先通过普通 `exec_checked()` 读取机器型号。存在待重启或结果待确认的事务时，
这条命令被 `FirmwareSSHClientWrapper` 拒绝，用户无法靠刷新获知实际状态。
断线后重连的页面状态会重置，也不会恢复原来的运行中轮询。

复现：设置固件保护原因后执行刷新，第一次读取就抛错，
`inspect_device()` 调用次数为零。

最小修复：将这一组固定只读探针纳入既有 `firmware_session()`，
绑定当前连接；不要放开普通写操作或任意命令。

### R5 / P2：KOReader 覆盖传输失败会损坏原文件

位置：`_koreader.py:899`；下载的同类路径为 `_ssh.py` 的 `download_file()`。

覆盖上传直接 `sftp.put()` 到最终路径。原文件先被打开截断，断线、写满或
传输错误之后只显示失败，原书已经被半个新文件替代。下载也是直接写最终
本地路径，覆盖时存在同样的原文件保护缺口。

复现：模拟传输写入 3 字节后断线，远端旧书被 3 字节的新文件替换。
上传失败场景有直接复现，下载结论来自对应调用路径审阅。

最小修复：同目录临时文件，完成传输和校验后再原子替换；服务端不支持
原子覆盖时停止操作并保留原文件。失败清理临时文件，不能提前销毁旧书。

### R6 / P2：批量文档准备失败会泄漏前面已复制的临时文件

位置：`_tab_documents.py:76`。

列表推导一次性准备全部文档。若第二个输入失败，赋值未完成，`packages`
仍为空，`finally` 遍历不到第一个已经创建的临时目录。反复失败会留下完整
PDF/EPUB 副本，占用电脑空间，也延长私人文档副本的存留时间。

复现：第一个输入准备成功、第二个输入抛错，第一份临时文档依然存在。

最小修复：逐个准备并立即 `append`，保留现有 `finally` 清理即可。

### R7 / P2：诊断包会把失败和截断误标为成功完整

位置：`_diagnostics.py:233`、`_diagnostics.py:248`。

远端命令由 `(命令) 2>&1 | tail -c 65536` 包装，返回的是 `tail` 的退出码，
不是采集命令的退出码。原命令失败时，清单仍可能标为 `ok`。
远端已经裁剪到上限，本地只有大于上限才设置 `truncated`，因此正常发生
的远端截断也不被标记。现有假 SSH 测试没有执行实际管道，未覆盖此行为。

复现：真实本地 POSIX shell 中 `exit 7` 被记录为成功；70,000 字节的输出
被裁成 65,536 字节后 `truncated=False`。

最小修复：显式传回采集退出状态，同时读取上限加一字节判断截断。
保留输出限额和只读白名单，不依赖未经确认的设备 shell 扩展。

## 优化建议

1. **优先补齐现有安全模式，而不是重构插件框架。** 文档删除与插件恢复页
   已有连接 token + 整批锁；KOReader 等页面复用这一模式即可。
2. **减少“检测全部插件”的重复读取。** `_tab_toolbox.py:5181` 逐项调用
   独立检测，每个功能又通过 `_tap_page_turn.py:570` 重读身份和计算 xochitl
   哈希。可先统计耗时，再在单次只读检测批次内复用身份/共享状态快照；
   写入前仍需重新验证，不能变成跨重启、跨设备的永久缓存。
3. **把剩余主线程网络操作放进已有 Worker。** 例如时间查询与设备控制
   仍直接执行 SSH；网络等待会阻塞 Qt 事件循环。沿用现有线程池即可。
4. **补齐发布验证的一致性。** Windows 构建只检查产物和证书文件，
   没有像 macOS workflow 那样运行打包程序的 `--https-smoke-test`。
   本轮人工补跑通过，但以后应由构建脚本自动执行两种 Windows 产物。
   顶层依赖虽已固定，传递依赖仍会更新；本次重建就下载了新的 cryptography、
   PyQt5-sip 和 PyInstaller hooks。建议记录解析后的版本，逐步形成可复现构建。
5. **更新 README 的发布号。** `README.md:16` 仍为 `v1.16.11`，与代码的
   `1.16.12` 不一致。无需因此单独重构文档系统。

不建议为了精简而删除已发布版本的信任信息、回滚检查、设备指纹和插件
保护标记；它们负责已有用户的安全迁移，不是可以随意删除的重复代码。
